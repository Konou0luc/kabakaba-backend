# Migration initiale unique et mise en service

> **État actuel.** `prisma/migrations/` contient **une seule migration**, `20261014083729_init`, plus
> `migration_lock.toml`. Elle a été générée par le moteur officiel de Prisma à partir de
> `prisma/schema.prisma` (36 tables, 12 enums, clés et index du schéma), puis complétée de l'index
> unique partiel des signalements (voir 1.1). L'ancien historique (28 dossiers) a été supprimé.
>
> **La partie 1 n'est donc plus à faire** : elle reste la procédure pour régénérer la migration si
> `prisma/schema.prisma` change avant la mise en service. **La partie 2 reste obligatoire** : cette
> migration se déploie sur une base **sans table**, jamais sur la base qui porte l'ancien
> `_prisma_migrations` (voir l'étape 2 de la partie 2).

Cette procédure ne s'applique qu'à une base **sans aucune donnée** (la production est vide, il n'y a
aucun client). Elle remplace l'historique de migrations ; elle n'est pas une migration de données.

> **La base de production a déjà été migrée avec l'ancien historique.** Elle est vide de données, mais elle
> contient les anciennes tables et la table `_prisma_migrations` de l'ancien historique : ce n'est **pas** une
> base sans table. Il faut donc d'abord la remplacer ou la réinitialiser (étape 2 de la partie 2).
> **Une base qui porte encore l'ancien `_prisma_migrations` ne doit jamais recevoir la nouvelle migration
> sans cette étape** : les tables existantes entreraient en conflit avec la migration.

## 1. Régénérer la migration initiale unique (poste de développement)

Prérequis : Node.js, accès Internet (téléchargement du moteur Prisma), dépôt à jour sur `main`
(dernier commit : « refactor: autorisations de cantine partagées, booléens d'URL, renommage de
escrow, commentaires et code sans usage », puis « chore: migration initiale unique, contrat d'API et
essais sur base réelle »).

**Option : script.** Un script `regenerer_migration.sh`, fourni à part, peut être placé à la racine du dépôt
backend (`kabakaba-backend/`) pour enchaîner les cinq étapes de cette partie : installation des dépendances,
génération de la migration, ajout de l'index partiel (1.1), vérification du SQL (1.2) et commit local (1.3). Il
n'est pas versionné dans ce dépôt ; les commandes ci-dessous restent la référence.

**L'ancien historique de migrations (`prisma/migrations/`, 28 dossiers) est supprimé du dépôt avec
la régénération** (étape 2 des commandes) : le dossier ne contient ensuite que la migration unique et
`migration_lock.toml`.

```bash
cd kabakaba-backend
git pull origin main

# 1. Dépendances (le postinstall lance `prisma generate`, qui lit DATABASE_URL_PROD :
#    une valeur factice suffit, aucune connexion n'est ouverte).
export DATABASE_URL_PROD="postgresql://u:p@localhost:5432/x"
npm ci

# 2. Conserver le fichier de verrou du fournisseur, supprimer l'ancien historique.
cp prisma/migrations/migration_lock.toml /tmp/migration_lock.toml
git rm -r -q prisma/migrations

# 3. Générer UNE migration à partir du schéma, sans base de données.
TS=$(date -u +%Y%m%d%H%M%S)
mkdir -p "prisma/migrations/${TS}_init"
npx prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script \
  > "prisma/migrations/${TS}_init/migration.sql"
#    Si cette version de Prisma refuse `--to-schema`, utiliser `--to-schema-datamodel`
#    (même résultat).

# 4. Restaurer le fichier de verrou (contenu attendu : voir plus bas).
cp /tmp/migration_lock.toml prisma/migrations/migration_lock.toml
```

Contenu attendu de `prisma/migrations/migration_lock.toml` (si le fichier est à recréer) :

```toml
# Please do not edit this file manually
# It should be added in your version-control system (e.g., Git)
provider = "postgresql"
```

### 1.1 Ajouter à la fin de `migration.sql` l'index unique partiel des signalements

Prisma ne sait pas décrire un index unique **partiel** (clause `WHERE`) dans `schema.prisma`. Cet
index, qui garantit « au plus un signalement non traité par commande » même en cas de requêtes
simultanées, doit donc être ajouté **à la main, tout à la fin** du fichier `migration.sql` (après la
dernière instruction générée), exactement tel quel :

```sql

-- Filet contre les doublons de signalement (cahier V1.3, section 35) : au plus un signalement non
-- traité (status <> 'RESOLVED') par commande. Prisma ne sait pas décrire un index unique partiel
-- (clause WHERE) dans schema.prisma : il est donc ajouté ici à la main et n'apparaît pas dans le
-- schéma. Toute régénération de cette migration doit conserver cette instruction. `prisma migrate
-- dev` et `prisma migrate diff` le signalent comme une différence entre la base et le schéma : ne
-- pas le supprimer.
CREATE UNIQUE INDEX "Report_orderId_open_key" ON "Report"("orderId") WHERE "status" <> 'RESOLVED';
```

> Conséquence à retenir : sur ce projet, utiliser **`prisma migrate deploy`** pour appliquer des
> migrations (jamais `migrate dev` ni `migrate reset` sur une base qui porte cet index sans
> vérifier le diff proposé).

### 1.2 Vérifier le contenu du SQL généré

Exécuter ce script depuis `kabakaba-backend` (il lit la migration la plus récente) ; il ne doit
afficher aucune ligne `MANQUE` ni `INTERDIT` et se terminer par `OK`.

```bash
F=$(ls -d prisma/migrations/*_init | tail -1)/migration.sql
ko=0
need() { grep -qE "$1" "$F" || { echo "MANQUE   : $2"; ko=1; }; }
deny() { grep -qE "$1" "$F" && { echo "INTERDIT : $2"; ko=1; }; }

# Tables et enums attendus
for t in ScheduledOrder Referral Report ComponentRupture Component ComponentCategory Menu MenuLine TakeawayOption; do
  need "CREATE TABLE \"$t\"" "table $t"
done
for e in ScheduledOrderStatus ReportType ReportStatus VendorCapacity ConsumptionMode ComponentUnit OrderCancelledBy; do
  need "CREATE TYPE \"$e\" AS ENUM" "enum $e"
done
# Colonnes et contraintes attendues
need '"unclaimedAt"'                      'Order.unclaimedAt'
need '"orderNumber"'                      'Order.orderNumber'
need '"activeOrderNumber"'                'Order.activeOrderNumber'
need 'Order_vendorId_activeOrderNumber_key' 'unicité (vendorId, activeOrderNumber)'
need '"referralCode"'                     'User.referralCode'
need 'User_referralCode_key'              'unicité User.referralCode'
need '"lastSchedulingReminderAt"'         'User.lastSchedulingReminderAt'
need 'Order_status_readyAt_idx'           'index Order(status, readyAt)'
for v in REFERRAL_BONUS SALE PAYMENT REFUND; do need "'$v'" "TransactionType.$v"; done
need 'Report_orderId_open_key'            'index unique partiel des signalements'
# Éléments qui ne doivent plus exister
for n in Ambassador Debt MenuItem MenuComponent Dispute VendorSchedule PackagingOption WithdrawalAppeal AbuseLog; do
  deny "\"$n\"" "$n"
done
# L'index partiel doit être la dernière instruction
tail -n 1 "$F" | grep -q 'Report_orderId_open_key' || { echo "MANQUE   : l'index partiel doit terminer le fichier"; ko=1; }
[ $ko -eq 0 ] && echo OK || exit 1
```

Contrôle équivalent déjà fait sur `prisma/schema.prisma` (état `fa1d4d4`) : les 9 tables, les 3 enums,
`Order.unclaimedAt`, `orderNumber`, `activeOrderNumber` avec `@@unique([vendorId, activeOrderNumber])`,
`User.referralCode @unique`, `User.lastSchedulingReminderAt`, `@@index([status, readyAt])` et les
valeurs `REFERRAL_BONUS`, `SALE`, `PAYMENT`, `REFUND` sont présents ; `Ambassador`, `AmbassadorAffiliate`,
`Debt`, `MenuItem`, `MenuComponent`, `Dispute`, `VendorSchedule`, `PackagingOption`,
`WithdrawalAppeal`, `AbuseLog` sont absents. Ce contrôle porte sur le schéma, pas sur le SQL, qui
reste à vérifier avec le script ci-dessus.

> Remarque sur l'unicité des numéros de commande : `Order.orderNumber` n'est **pas** unique à lui
> seul (un numéro est réutilisé dès qu'une commande de la cantine est « Récupérée » ou « Annulée »).
> La contrainte est `UNIQUE (vendorId, activeOrderNumber)`, où `activeOrderNumber` vaut `orderNumber`
> tant que la commande est active et `NULL` ensuite (PostgreSQL admet plusieurs `NULL`).

### 1.3 Valider et publier

```bash
git add -A prisma/migrations
git diff --cached --stat            # l'ancien dossier supprimé, le nouveau créé
npm run build                       # génère le client et compile
git commit -m "chore: migration initiale unique"   # ou rattacher au commit de l'étape 27
git push origin main
```

## 2. Appliquer la migration sur une base vide (Neon)

À faire **une seule fois**, sur une base de production **sans donnée et sans table**, après la partie 1 (l'étape 2
ci-dessous explique comment obtenir une telle base à partir de la production actuelle).

1. **Sauvegarde.** Même vide, créer une branche de sauvegarde Neon (ou un point de restauration) avant
   toute opération : `Neon > Branches > Create branch` à partir de la branche de production.
2. **Repartir d'une base sans table.** La production a déjà été migrée avec l'ancien historique : elle ne
   contient aucune donnée utile, mais elle porte les anciennes tables (`Ambassador`, `Debt`, `Dispute`…) et
   l'ancienne table `_prisma_migrations`. Choisir l'une des deux options.

   - **Option A (recommandée) : créer une nouvelle base vide** dans le même projet Neon (console Neon,
     `Databases`, nouvelle base). Utiliser **sa** chaîne de connexion : la chaîne **directe** (sans `-pooler`
     dans le nom d'hôte) pour `prisma migrate deploy` à l'étape 4, puis la chaîne du **pooler** dans
     `DATABASE_URL_PROD` sur Vercel à l'étape 6. L'ancienne base reste intacte et peut être supprimée plus
     tard. Aucune vérification de données n'est nécessaire : la base est neuve.
   - **Option B : réinitialiser le schéma de la base existante**, **uniquement après avoir vérifié qu'elle ne
     contient aucune donnée utile**, et **après la sauvegarde par branche Neon de l'étape 1**. Avec l'URL
     **directe**, compter les lignes des tables qui porteraient des données réelles (le solde des étudiants
     est la colonne `User.walletBalance` : il n'existe pas de table `Wallet`) :
     ```bash
     psql "$URL_DIRECTE" -c 'SELECT (SELECT count(*) FROM "User") AS users, (SELECT count(*) FROM "Order") AS orders, (SELECT count(*) FROM "Transaction") AS transactions, (SELECT count(*) FROM "User" WHERE "walletBalance" <> 0) AS users_avec_solde;'
     ```
     Si l'une de ces valeurs n'est pas `0`, **s'arrêter** : choisir l'option A. La commande suivante supprime
     aussi les comptes d'administration web (`WebUser`), les campus (`Campus`) et tout le reste du schéma
     `public` : les compter (`SELECT count(*) FROM "WebUser";`, `SELECT count(*) FROM "Campus";`) et prévoir de
     les recréer après la migration. Réinitialiser alors le schéma, avec le rôle propriétaire de la base :
     ```bash
     psql "$URL_DIRECTE" -c 'DROP SCHEMA public CASCADE; CREATE SCHEMA public;'
     ```
     Cette opération est irréversible (hors restauration de la branche de sauvegarde).

   Dans les deux cas, l'ancien historique de migrations n'existe plus dans le dépôt (partie 1) et l'ancienne
   table `_prisma_migrations` ne doit plus exister dans la base visée : l'étape 3 le contrôle.
3. **Vérifier que la base est vide.** Avec l'URL **directe** de la base (pas l'URL du pooler) :
   ```bash
   psql "$URL_DIRECTE" -c "SELECT count(*) FROM information_schema.tables WHERE table_schema = 'public';"
   ```
   Résultat attendu : `0`. **Si la base contient des tables (la table `_prisma_migrations` de l'ancien
   historique comprise) ou des données, s'arrêter** et reprendre l'étape 2 : cette procédure ne s'applique
   qu'à une base sans donnée et sans table.
4. **Appliquer la migration.** `prisma migrate deploy` utilise `DATABASE_URL_PROD` : y mettre l'URL
   **directe** de la base visée à l'étape 2 (la variante sans `-pooler` dans le nom d'hôte Neon), le temps de la
   commande :
   ```bash
   cd kabakaba-backend
   export DATABASE_URL_PROD="postgresql://<utilisateur>:<mot_de_passe>@<hôte-direct>/<base>?sslmode=require"
   npx prisma migrate deploy
   ```
   Résultat attendu : « 1 migration found in prisma/migrations » puis « All migrations have been
   successfully applied ». Ne pas utiliser `migrate dev` ni `migrate reset`.
5. **Vérifier les tables et l'index partiel.**
   ```bash
   psql "$URL_DIRECTE" -c "\dt" | head -60
   psql "$URL_DIRECTE" -c "\d \"Report\""        # doit lister Report_orderId_open_key avec le prédicat WHERE
   psql "$URL_DIRECTE" -c "SELECT migration_name, finished_at FROM _prisma_migrations;"   # une ligne, finished_at renseigné
   ```
   Contrôles minimaux : les tables `ScheduledOrder`, `Referral`, `Report`, `ComponentRupture`,
   `Component`, `ComponentCategory`, `Menu`, `MenuLine`, `TakeawayOption` existent ; aucune table
   `Ambassador`, `Debt`, `MenuItem`, `MenuComponent`, `Dispute`, `VendorSchedule`, `PackagingOption`,
   `WithdrawalAppeal`, `AbuseLog`.
6. **Remettre l'URL du pooler** dans `DATABASE_URL_PROD` sur Vercel (c'est l'URL de l'application ; avec l'option A, celle de la
   **nouvelle** base) et ne pas conserver l'URL directe dans un fichier du dépôt.
7. **Générer le client.** Il est généré à chaque build (`npm run build` lance `prisma generate`) ;
   en local, `npx prisma generate`.
8. **Passer aux essais.** Dérouler `docs/ESSAIS_BASE_REELLE.md` avant d'ouvrir l'application aux
   utilisateurs.

Réactivation des workflows : `scheduled-orders.yml`, `unclaimed-orders.yml` et
`scheduling-reminders.yml` interrogent des tables qui n'existent qu'après cette migration. S'ils ont
été désactivés en attendant, les réactiver une fois les vérifications de l'étape 5 passées (onglet
Actions de GitHub).

## 3. Changements de schéma ultérieurs

Une fois la base en service (avec des données), toute évolution du schéma passe par une **nouvelle
migration** créée sur un poste de développement, relue, puis appliquée avec `prisma migrate deploy`.
Elle doit conserver l'index `Report_orderId_open_key` (voir 1.1). La procédure de la partie 2 (base
vide) ne doit alors **plus** être utilisée.
